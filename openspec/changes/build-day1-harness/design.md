# Design

## Context

动机与范围见 [proposal.md](./proposal.md)。当前项目没有自己的 Go 实现和测试；根目录的 [SPEC.md](../../../SPEC.md) 与 [PRINCIPLES.md](../../../PRINCIPLES.md) 是本次拆分的依据，`.research/` 是只读参考。

本 change 的八项 delta specs 描述待交付行为。创建规划文件不代表功能完成；全部实现任务从未完成开始。根目录文档保留为讨论基线，发现冲突时先修订提案，不能让实现者自行选择两种相反行为。

## Goals / Non-Goals

**Goals:**

- 把状态所有权、持久接受、调用生效和恢复边界固定下来，让 CLI、TUI 与模型共用一套业务入口。
- 先验证“模型执行命令 → 界面断开重连 → core 重启后续接”的纵向路径，再补齐全部 Day1 能力。
- 用公共行为测试约束四协议适配，用故障注入验证恢复，而不是只测正常工具调用。

**Non-Goals:**

- 不移植参考项目的完整实现，也不依靠构建参考仓库证明本项目正确。
- 不做巨型跨供应商 IR、所有事件共用的 phase、通用后台任务总管或任意 Go 代码热替换。
- 不把 SQLite、JSON-RPC 或命令拼写写成产品原则；以下是本提案选择的工程方案，可在不改变行为的前提下修订。

## Decisions

### D1. 单一后台 core，进程运行由独立 runner 承担

采用 Go、Bubble Tea v2，Linux 本机每个配置档一个 core。TUI 与短命 CLI 连接同一个 core；core 不导入 Bubble Tea。模块按既有边界落地，不为每个能力另建服务：

| 模块 | 拥有的状态或职责 |
| --- | --- |
| `runtime` | Agent、Task、调度、mailbox、停止与恢复协调 |
| `model` | 公共模型事件、四协议 adapter、预算与输出分类 |
| `tool` | 小型工具集合、调用参数校验、执行关联 |
| `process` | 独立 runner、tmux PTY、pipe、输入输出和退出记录 |
| `resource` | 配置合成、资源目录、MCP、skill、插件版本 |
| `protocol` | CLI/TUI 命令及事件传输 |
| `store` | 历史、状态、去重、资源版本、压缩视图及查询 |
| `render` | Bubble Tea 状态投影与 alt-screen 展示 |

Agent 与 Process 各自管理生命周期，共享身份关联与事件记录，不把二者压成一个万能后台任务。一个 Agent 是一个持续会话，`agent_id` 同时作为会话 ID；同一 Agent 只推进一条模型循环。`task_id`、`process_id`、`message_id` 只表达真正不同的对象。

runner 与 core 分开存活，不能因 core IPC 关闭就退出。启动记录包含配置档、runner 实例身份、连接位置及其管理的进程；core 重启后先查询 runner，再决定是否继续任务。客户端可在后台服务缺失时启动服务，但连接重试不能创建多个同配置档 core；启动锁与运行身份需要测试。

没有选择“所有 goroutine 都挂在 TUI”是因为断开界面必须不影响工作；没有把 tmux pane 当 Agent，是因为会话历史、模型状态和 mailbox 仍由 core 管理。

### D2. 本地 JSON-RPC 控制接口，事件按会话游标补发

采用 Unix domain socket 上的 JSON-RPC，命令响应与事件通知共用明确版本的协议。只实现本地传输；不交付公网控制端口。一个传输请求 ID 用于匹配响应，另有跨重试稳定的操作请求 ID 用于持久去重，两者不混淆。

命令至少携带协议版本、操作名、请求 ID、目标身份和参数；结果区分 accepted、running、completed、failed、unknown，而不是把 CLI 成功退出当作任务完成。统一错误表达错误码、可读说明、关联身份和是否可重试；内部错误细节不携带凭据值。

事件只统一 `schema_version / agent_id / seq / kind / payload`，任务、调用、进程身份按事件需要附加。seq 在会话内单调递增；全局订阅返回各 Agent 的游标，不再发明第二套全局事实顺序。客户端先取带游标的状态，再从游标订阅，服务在同一提交边界生成状态位置。可补发事件重传并去重，不重放命令。

CLI 暂用 `zende`，协作参数沿用根规格第 4.2 节；新增资源、配置、进程和上下文命令复用相同服务：

```text
zende agent spawn|send|inspect|history|wait|stop|resume
zende mailbox list
zende events watch
zende process inspect|output|stdin|resize|terminate
zende resource register|refresh|status|list|read
zende config inspect
zende context inspect|compact
```

长文本从文件或 stdin 读取，结构结果走 stdout、诊断走 stderr。参数校验和能力说明从注册信息生成或测试校对；不存在的命令不能进入提示词。没有选择仅 SSE，因为输入、取消和 resize 需要控制通道；也不要求新增一套与 CLI 等价的 Agent tools。

### D3. 一个持久事实来源，区分历史与可更新的状态投影

采用 SQLite 存储会话、任务、请求去重、mailbox、语义事件、资源版本与上下文视图；大输出使用文件及偏移引用，JSONL 只用于导出。追加历史与可更新的当前状态分开：修改“当前任务状态”投影不等于改写历史，但每次变化都追加事件。

接受输入与创建任务、消息进入上下文与更新投递位置、子任务完成与创建结果消息在事务内提交。大输出先持久写入，再提交可读取范围；恢复时校验引用长度，未完整落盘区间明确报告。高频 PTY 字节不逐字进入数据库或模型历史，语义事件携带输出位置即可。

原始请求历史、摘要和工具结果不做静默清理。输出轮转只释放不再被保留引用使用的内容；容量不足返回资源错误而非删掉仍被任务依赖的结果。配置及凭据绑定只记录引用，序列化、日志和导出路径共用凭据脱敏处理。

没有选择“JSONL 和数据库各写一份权威记录”，以免接受确认与恢复选择发生分歧。文件输出与数据库仍不是一个原子写入域，因此必须保留缺口检查，不能宣称完整跨介质事务。

### D4. 进程运行、输出记录与 patch 各自负责

runner 为每条命令记录稳定身份、cwd、环境引用、PTY/pipe 类型、输入状态、输出位置、启动信息和终态。初次等待超时只返回仍在运行的身份；继续输入与观察不重新执行命令。对同一进程的输入和控制操作有序派发，不同无依赖进程可并行。

PTY 采用受 runner 管理的 tmux session/pane，记录 tmux server/session/pane 与本地进程身份的映射。使用可持续采集输出的连接，并在命令开始前建立输出记录；终态由 runner 的退出记录或可验证的 tmux 状态提供。`capture-pane` 只是辅助快照。pipe 的文件描述符由 runner 持有。runner 本身故障时报告可确认的终态、仍可关联的 PTY 或丢失进程，不伪造 pipe 可无损恢复。

基础工具保持小型集合：执行、继续输入/读输出、patch、MCP 搜索和调用；resize、终止、状态查询同时向 CLI 开放。图片观察按实际任务和 provider 能力接入，不作为四协议共同验收的额外多模态要求。

patch 先解析并校验全部变更的旧内容与目标冲突，再应用并报告文件级结果。校验失败不写文件；写入阶段发生 I/O 故障必须报告已生效范围，不宣称跨文件原子事务。patch 不依赖 Git，shell 生成器与其他写入程序继续可用。它是默认文本编辑协议，不是执行权限机制。

没有选择“所有命令都用 PTY”，因为 pipe 保留 stdout/stderr 边界且更适合非交互输出；没有选择“只有 patch 能写”，因为这会破坏真实环境中的生成、格式化和构建能力。

### D5. 协作走 CLI，mailbox 保证投递，wait 查询结果

spawn 从父 Agent 一致历史边界建立继承快照，再追加子身份与任务。`all` 指父当前可继承视图；压缩过的历史不自动重新展开。`none / last:N / context-budget` 与自定义背景均可用，计算预算后报告实际选择，不切断消息或调用对。

默认 cwd 取父 Agent 的有效工作环境，不取一次 CLI 的临时 cwd。worktree 使用显式目录和创建结果记录，失败报错，完成后不自动合并或删除。

mailbox 用稳定 message ID 保存长期通信。queue 在任务终态后处理；steer 在当前响应及所需工具调用全部落定后的下一请求边界注入，不负责终止进程。stop 取消当前 Task 并设人工暂停，子 Agent 和已交接的后台进程继续。resume 新建任务，旧 cancelled 记录保持不变。

子任务终态与结果消息在同一事务提交。wait 直接查询指定任务，不依赖父 mailbox 消费。host 给模型执行的 CLI 提供归因绑定，并由服务记录 wait 返回的结果消息身份；只有关联工具结果确实进入父上下文时，才原子标记该消息已投递。仅看到 CLI stdout、只返回了不可读引用或工具结果丢失，不能提前消费消息。这条关联使用服务元数据，不依赖解析任意 shell 文本猜测。

没有选择“所有子结果马上打断父 Agent”，因为 queue 与 steer 是不同意图；没有让 wait 等 mailbox ack，因为父任务可能正阻塞于 wait 本身。

### D6. 小型公共模型语义，协议私有数据单独保留

公共层只描述合法消息、文本增量、调用参数增量、工具结果、用量、取消和错误。每个 adapter 自己保存续接、不透明签名及供应商消息结构。迁移 provider 重新构造合法请求，无法转移的能力明确报错；不能把私有数据变成正文后交给另一家。

先实现共同测试夹具，再逐个接入 Responses、Chat Completions、Anthropic Messages、Gemini。四协议都跑相同的多轮调用、错误、取消、预算、MCP 和输出分类用例。可选能力按端点和模型配置声明；真实协议字段以实现时对应接口资料与可用端点验证为准，本提案不声称所有兼容服务支持官方可选扩展。

commentary/final 的原生语义经过验证就直接映射，否则使用显式标签适配。解析器只处理模型可见正文，缓冲跨片段行；原始字节另存，解析层统一识别 LF/CRLF。独立起止标签无缩进或引用前缀，代码围栏与反斜杠转义内容不作控制。合法 final 在闭合后仍要等响应完成，才能确认没有后续非法内容或冲突调用。

首次格式错误保留原文，最多追加一次修复请求；仍不合法则返回可恢复格式错误。修复不重放已执行调用；final 与工具调用冲突时暂停完成判定，补齐现有调用状态后要求模型明确下一步。修复次数属于本提案工程默认值，可配置，不改变“有界且不猜测 final”的要求。

没有选择通过 finish reason 推断，因为传输完成不代表业务完成；没有用 JSON 包装所有文字，因为会限制自然流式输出，也不能替代协议侧工具调用。

### D7. 配置与能力目录分开生效

配置采用 YAML。本提案采用如下层级，从低到高合成：默认值 → 配置档用户设置 → 项目设置 → 项目本地覆盖 → 环境变量 → CLI → 本次任务覆盖。map 按键覆盖、列表整体替换、标量后者覆盖；非法类型和未知字段报校验错误，不静默忽略。查询包含有效值及来源，不包含展开后的凭据值。

用户配置、运行数据分别放入对应的 XDG 配置/状态目录下 `zende/<profile>/`，IPC 放入用户运行时目录；项目配置拟用 `.zende/config.yaml`，本地覆盖用 `.zende/config.local.yaml`。具体绝对路径由运行环境解析并可查询，不能在实现中硬编码本机用户名。安装包和资源与运行输出分开存放。

每次请求从当前已发布目录选择资源版本，开始后持有版本引用直到结束。任务启动设置用于追溯和默认运行选择，不冻结资源目录；新增 MCP、skill、provider 或插件立即可发现。默认模型和 cwd 不随配置刷新改变当前任务，显式选择才在后续合法边界生效。

安装或刷新经过准备、校验、连接/初始化、发布四步。显式 register/refresh 可返回进度或等待 ready，外部文件修改由监视器合并事件并校验完整性；无论入口都共用发布流程。失败保留旧版本，新发布仅追加有界变化通知。

没有选择“整个 Task 固定可用能力”，因为这会直接违背同任务安装即用；没有选择“配置一变所有运行选择立即切换”，因为它会破坏正在执行的请求和工作环境。

### D8. MCP 保留目录，插件保留独立生命周期

MCP host 维护工具目录与有界搜索。`tool_ref` 包含或解析到稳定目标及定义版本；目录 generation 只说明发现时的目录，不等于全部引用统一失效。执行时校验引用和 schema；目标过期返回 stale-reference。host 搜索/调用是四协议兜底，已验证支持原生 deferred/tool search 的接入默认走原生路径，仍由同一目录与调用记录承接。

skill 发布名称、描述、正文和资源入口；模型先读指令再使用，脚本仍是普通进程。prompt/skill 的应用以带来源的追加内容表达，不改写旧提示词列表。

插件使用版本化 JSON-RPC over stdio，stdout 只传协议，stderr 记录诊断。协议覆盖初始化、能力发现、调用/进度、取消、事件订阅、关闭；同一协议容纳不同能力类型，但不抹平 provider 流、CLI 结果与资源读取的差别。新版 ready 后发布，旧调用持有旧实例，引用释放后再回收。

没有选择同进程 Go 插件或任意代码热替换，因为独立进程更容易界定崩溃与替换边界；没有把 MCP 全部展开或 Day1 引入 CodeMode，因为稳定的搜索/调用入口已能形成闭环。

### D9. 压缩切换视图，恢复先查事实

压缩从完整消息及工具对的边界取历史前段，生成包含原文引用的摘要，验证后提交新视图；生成期间新增记录作为尾部追加。摘要失败保留旧视图。有空间才允许重试，容量不足停在可恢复错误上，不清空会话。

工具派发前保存执行意图和稳定调用 ID，派发后记录外部关联与结果。core 重启时先检查已有结果及 runner，再决定恢复位置。模型流中断保留片段并标记不完整；不能续接时从合法边界重新请求，不把两个响应拼成虚假的完整回答。

结果未知的有副作用操作进入待核实状态。受影响 Task 暂停普通执行循环，先查已有进程、调用结果或明确的产物证据；不能确认安全继续时保留待处理并报告。另起调用 ID 不会解除该状态。这里依赖持久状态和证据，不承诺通过命令字符串比较就能识别所有等价操作，也不是为正常工作引入审批管理器。

没有选择统一自动重试所有失败，因为远端效果不具备普遍 exactly-once 保证；恢复承诺是保住上下文并继续可确认的工作。

### D10. TUI 是可替换客户端

Bubble Tea v2 的 Update 只接收状态和事件投影；模型请求、进程等待、插件调用及数据库访问都在界面之外。TUI 默认 alt screen，退出恢复终端但不停止后台。

普通进程视图展示有界日志与状态，不把 PTY 原始 ANSI 直接写 renderer。需要完整交互时提供显式 terminal handoff，临时交出并恢复终端；回到 TUI 后按游标补齐事件。窗口尺寸先更新布局，只有明确控制目标时才向该 PTY 发送 resize，多个只读观察者不争抢终端尺寸。

常驻布局为对话、组合输入框和下方状态栏。正文及次要文字保持绿色，颜色取 `.design/tui-preview/theme.js`；窗口按终端单元格布局，覆盖 80×24、60 列和 48×16。字体由终端选择，图标缺字有普通字符回退。后台 Agent/Task/tmux 聚合显示，警告按需展开，错误首次展开，commentary 折叠仅改变展示。

命令 registry 同时驱动 `/` 搜索、点击及快捷键，所有点击入口都有 `/` 路径。候选从组合输入下方展开；`$` 读取 skill 目录。主输入和提问复用组件，草稿与附件按用途独立保存；中文 IME 与多行输入不误提交。终端图片通过可用剪贴板桥接或文件附件入口导入，不支持的模型保留草稿并报错。

模型选择读取有效配置，以连接 ID 区分同厂商端点，按连接→型号→思考力度选择，最终确认才提交。空配置不造模型。目录选择只有当前页，`.` 选当前目录，`..` 上一级，支持键盘和路径输入；浏览不改变 Agent cwd。

会话复制是 core 的持久操作：校验目标→记录复制意图并冻结原会话新输入/调度→停止所属 Agent 树及进程→核实终态→在事务中复制历史/上下文与附件引用、发布新 Agent。源历史保留为只读；新副本继承可合法继续的上下文，不重放已完成副作用。正在执行而结果未知的操作先走核实流程。取消确认没有操作；停止失败保留待处理记录，重试复用操作 ID，副本发布前不启动新工作。普通 stop、detach 不受此流程影响。

### D11. 提示词与注册能力一起维护

参考 Pi 提交 `7bc154ad082e2f0029c19117a16d22a504439476` 的 `packages/coding-agent/src/core/system-prompt.ts` 和 `src/core/tools/`：工具 descriptor 保存短说明与使用规则，系统提示词只组合已注册能力并去重共同规则。借鉴组织方式，保持 Zende 的终端/进程/patch 工具边界。

基础系统说明、输出分类规则、协作常用命令、项目指令和 skill 目录分别维护。协作说明包含时机、默认值、queue/steer、wait 和结果回流；低频参数用帮助查询。工具说明给出输入、结果、截断/等待及错误后的行动。通过测试检查提示词与命令、参数默认值一致。资源更新追加来源和版本，不原地替换历史。文案按 trim-cn-tech-doc 精简，保留协议词和失败条件。

## Risks / Trade-offs

- [Day1 范围大] → 分组实现并验证八项能力与 V01–V23，实施顺序不缩减交付范围。
- [tmux 输出采集、退出记录、runner 重连存在竞态] → 在最早进程里程碑用真实 tmux/pipe 测试短命令快速退出、输出爆发、core 崩溃和身份失效；记录可验证输出范围。
- [数据库与大输出文件不能一次提交] → 输出先落盘、提交引用、恢复校验，截断或缺失显式返回。
- [显式标签可能与正文冲突] → 行边界、围栏、引用和转义测试；保留原文、有界修复，不猜测终态。
- [热更新增加版本保留开销] → 只保留活动请求/调用和历史引用需要的定义或实例；旧实例退役可查询，不能为了回收强杀旧调用。
- [外部副作用不可统一去重] → 未知状态暂停原任务推进，先核实，不宣称任意外部系统 exactly-once。
- [可信工具可能泄露敏感数据] → 凭据引用与受管理序列化脱敏必须测试；无沙箱不等于任意第三方程序都能被宿主保证安全。
- [多协议真实端点和凭据未提供] → 可重复夹具测试与真实端点验证分开记录；缺少授权或环境时明确未验证，不用 HTTP 200 或模拟响应冒充真实兼容性结论。

## Migration Plan

用户已批准实施，按以下顺序推进：

1. 建立 Go 模块、版本化接口与存储，验证客户端、core、runner 的独立生命周期。
2. 使用确定性模型夹具接通执行、输出和重连，再接入第一个真实协议；不把其他三个移出 Day1。
3. 加入协作、资源即时发布、插件和压缩，补齐其余协议，共用验收集合。
4. 按独立临时配置档执行故障注入与端到端验证，保留日志和未通过项。
   将二进制安装到用户级目录，提供显式 core/runner 启停与接回入口，不写生产凭据或开放公网控制端口。安装前检查旧版本，更新时保留可恢复副本；真实模型验证单独记录端点授权与结果，配置缺失不阻止本机夹具测试。
5. 用户确认实现完成后再走 OpenSpec 同步/归档流程；本 change 不提前把规划当作主规格的已交付事实。

运行数据采用带版本的 schema。首次发布无需兼容旧版本，但后续升级须先备份并验证兼容性；回退使用兼容二进制或备份，不让旧程序直接修改不认识的新 schema。停止/回退进程必须明确目标，不顺便删历史、worktree 或任务产物。
